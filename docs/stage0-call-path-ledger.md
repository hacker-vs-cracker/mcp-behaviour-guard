# Stage 0 call-path disposition ledger

This ledger records the current execution and evidence disposition of the major Stage 0 paths. It is
a closure record, not a proposal to route every operation through one universal gate.

"Audited" here means the path has an explicit disposition, safety/evidence boundary, and supporting
tests or rationale. Different paths intentionally use different mechanisms.

| Path | What authorizes execution | Evidence/gate before execution | What can degrade later | Known limitation | Existing test/rationale |
|---|---|---|---|---|---|
| Discovery / contract generation | Explicit `mcp-guard contract generate` parameters and discovery credential input. The generated draft itself is not trusted policy. | Server/identity models must validate and discovery must connect/list tools. Generated permissions and side-effect rules remain conservative and require human review. | Discovery failure exits non-success; this path does not create a security-conformance finding. | MCP metadata cannot define the organisation's real authorization policy; native import from every agent host is not implemented. | `tests/test_contract_tools.py`, `tests/test_stdio_client.py`, restricted HTTP/STDIO transport tests. |
| `doctor` connectivity | Explicit user invocation with an optional reviewed contract. | Contract loading plus `validate_target(..., lab_mode=False)` when a contract is supplied. HTTP checks the derived health endpoint; STDIO initializes and lists tools. | Availability can fail at runtime and is reported as diagnostic status. | Connectivity is not proof of authorization, isolation, or safe behaviour. | Runtime/client/safety and restricted transport tests. |
| Ordinary authorization / tool probes | Reviewed contract tool definitions, selected identities, probe arguments, and the engine's invocation safety gates. | Invocation safety is evaluated before target execution. Mutation/effect observation preflight runs where the declared claim requires it; an ordinary read-only authorization call can execute with observation `not_required`, while read-only behaviour/effect claims are evaluated separately. Denial conclusions require relevant positive-control semantics. | Observer/runtime failure can downgrade absence claims to error/inconclusive; confirmed effects are retained. | Only configured identities, arguments, claims, and observers are tested. | `tests/test_engine_rules.py`, `tests/test_evidence_semantics.py`, `tests/test_denial_confidentiality.py`, `tests/test_observation_preflight.py`, `tests/test_side_effect_claims.py`. |
| Tenant probes | Explicit `tenant_probes` in the reviewed tool contract, including the chosen identity and resource arguments. | The same target/tool safety boundary applies; required observation is preflighted when the declared claim needs it. | Later execution/observation errors can reduce assurance, but confirmed cross-tenant disclosure is not converted into a pass. | Coverage is limited to the configured tenant/resource probes; it is not universal tenant enumeration. | `tests/test_c3b_tenant_confidentiality.py`, `tests/test_evidence_semantics.py`, observation-preflight tests. |
| Policy probes | Explicit reviewed `policy_probes` and their declared checks. | Tool-call safety and required evidence are evaluated before the probe. | Missing/malformed required evidence produces non-pass rather than silently approving the check. | Only the declared policy checks are exercised. | `tests/test_engine_rules.py`, `tests/test_evidence_semantics.py`, `tests/test_observation_preflight.py`. |
| Session probes | Explicit `session_tests` with reviewed writer/reader identities, tools, arguments, and marker semantics. | Write/read call safety and configured evidence requirements are checked before execution. | Confirmed cross-session marker disclosure remains a failure even if later execution or observation also errors. | Tests the configured marker flow and sessions, not every possible server-side state channel. | `tests/test_evidence_semantics.py`, `tests/test_engine_rules.py`, session safety/preflight coverage. |
| Replay probes | Explicit replay configuration plus the normal tool contract. State-changing execution remains behind the destructive/lab safety boundary. | Replay preflight requires the replay event and relevant tool side-effect claims to have the needed observation coverage before execution. | Missing/insufficient effect evidence is non-success; a zero-observation run is not accepted as proof of replay safety. | Replay assurance depends on the configured operation, effect claims, and observer visibility. | `tests/test_n1_replay_side_effect_evidence.py`, `tests/test_observation_preflight.py`, `tests/test_safety_gate.py`. |
| Temporal `invoke_on_session` | `temporal_integrity.enabled`, a reviewed driver tool, selected permitted identity, and contract validation requiring a read-only driver. | The driver must pass the engine invocation gate before a persistent session is opened for repeated calls. | Invocation errors and metadata-discovery failures are retained; observed metadata drift remains evidence. | Finite sessions/calls can detect observed drift but cannot prove that no later/conditional trigger exists. | `tests/test_temporal.py`, `tests/test_temporal_contract.py`, `tests/test_temporal_engine.py`, `tests/test_client_metadata.py`. |
| Active baseline capture | Explicit `baseline capture/compare`, a reviewed contract, and target validation. | Read-only probes can run normally; a state-changing baseline probe is skipped unless the existing lab/destructive safety boundary permits it. Configured observers participate. | Observer/transport failure can make the active capture incomplete or fail rather than fabricate absence. | This path contacts the target and is not the offline saved-run comparator or an independent approval authority. | `tests/test_baseline.py`, R9 ownership/correlation tests. |
| Observer begin/reset/collect | Declared observer configuration plus the current run/check/operation scope. | Required observation is preflighted for claims that need it; same-host/same-user ownership serialization and correlation are used where configured. | Partial/malformed later telemetry can degrade absence assurance, while previously confirmed events are retained. | Visibility is limited to configured sources/paths and current ownership/correlation boundaries; it is not OS-wide syscall monitoring. | `tests/test_observer_integrity.py`, `tests/test_c4_jsonl_one_shot_retention.py`, `tests/test_r9_observer_concurrency.py`, `tests/test_r9b_observer_settling.py`, `tests/test_r9c_correlated_attribution.py`, `tests/test_r9c_http_correlated_attribution.py`. |
| Cleanup / cancellation | Structured client/session, ownership, observer, and storage lifecycles around an already-authorized operation. | Cleanup is entered through the same context managers/finally paths as the operation; it does not add a new authorization decision. | Cancellation or transport failure can interrupt local work; cleanup preserves local ownership/storage invariants where implemented. | Guard cannot roll back arbitrary remote side effects that already occurred before cancellation. | `tests/test_r9_observer_concurrency.py`, `tests/test_r9b_observer_settling.py`, and `tests/test_r10_restricted_stdio_launch.py`. |

## Closure interpretation

The ledger supports these bounded statements:

- Stage 0 correctness fixes can remain closed without an engine-wide gate rewrite.
- Diagnostic/discovery paths are not represented as security approval paths.
- Potentially state-changing test paths retain their existing safety and evidence preflight boundaries.
- Confirmed violations are not silently erased by later observation uncertainty.
- Evidence absence is only as strong as the configured observer coverage.
- Cleanup/cancellation cannot promise rollback of external side effects.

It does **not** claim that every path uses a single helper or that the current repository/CI provides
an independent approval authority. The latter is a separate trust-boundary problem for later work.
